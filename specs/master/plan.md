# Implementation Plan: Nutrition UX & Platform Quality Initiative

**Branch**: `master` | **Date**: 2026-04-06 | **Spec**: `specs/master/spec.md`
**Individual Specs**: `.specify/integrations/claude/specs/001–004`

## Summary

Four interconnected improvements to the MounTrack nutrition module, in priority order:

| # | Feature | Priority | Dependencies |
|---|---------|----------|-------------|
| 001 | Diary UI/UX redesign (FatSecret-parity) | P1 | None |
| 002 | Food search precision + source filtering | P1 | None (parallel with 001) |
| 003 | Retroactive diary editing | P2 | Extends 001's editable UI |
| 004 | Dedicated support / SAC section | P2 | None (fully independent) |

**Key finding**: The diary-items API (`POST /api/nutrition/diary-items`) already accepts any
`YYYY-MM-DD` date with no today-only guard. Retroactive editing is an API-ready UI problem, not
a backend problem.

## Implementation Sequence

### Feature 002 — Food Search (Independent, Start First)

**Why first**: Fully independent, unblocks daily-use improvements immediately.

**Steps**:
1. Add `source?: "fatsecret" | "openfoodfacts" | "usda" | "custom" | "all"` param to
   `GET /api/nutrition/foods/search` route.
2. Pass source filter through `CatalogSearchService` → `FoodSearchService.searchFoods()`.
3. Add debounce (300ms) and session-level result cache to `FoodSearchPanel`.
4. Add `SourceFilterChips` component below search bar in results view.
5. Add barcode-miss messaging in `useNutritionSearch` with "Adicionar Manualmente" CTA.

**Tests required**:
- Unit: `food-search.service.ts` — source filter narrows results correctly.
- Unit: `SourceFilterChips` — selected source emits correct filter value.
- Integration: `GET /api/nutrition/foods/search?source=custom` returns only custom foods.
- Integration: barcode miss triggers `onNomatch` callback with pre-filled barcode value.

---

### Feature 001 — Diary UI Redesign

**Steps**:
1. Create `MealSectionHeader` with: meal icon, meal label, calorie total (hidden when 0 items),
   expand/collapse chevron, and `+` button.
2. Create `DiaryItemRow` with: food name, quantity+unit (green), kcal value, and swipe-reveal
   delete/edit button area.
3. Update `DiaryTodayView` to use `MealSectionHeader` and `DiaryItemRow`.
4. Update `FoodSearchResultsSection` result rows: name (bold), serving (green), IDR%, kcal.
5. Update `NutritionHeader` (or equivalent summary area) to show macros: P/C/G vs. goals.

**Tests required**:
- Unit: `MealSectionHeader` — shows calorie total only when items > 0.
- Unit: `DiaryItemRow` — delete action fires callback with correct item ID.
- Unit: `FoodSearchResultsSection` — result row renders IDR% when goal is set; hides when not.
- Snapshot: `DiaryTodayView` with 0 items and with items (both states).

---

### Feature 003 — Retroactive Diary Editing (depends on 001)

**Steps**:
1. Create `DatePickerModal` — calendar input using native `<input type="date">` constrained
   to `max={yesterday}`, styled with DaisyUI. Returns selected `YYYY-MM-DD` string.
2. Add calendar icon to `DiaryHistoryView` header that opens `DatePickerModal`.
3. Create `RetroactiveDiaryView` — renders same meal sections as `DiaryTodayView` but receives
   `targetDate` prop; uses same `+` / edit / delete flows with `targetDate` forwarded to APIs.
4. Make `HistoryEntryCard` tappable — opens `RetroactiveDiaryView` for that date.
5. Update `CustomWaterDialog` to accept optional `targetDate: string` prop; PATCH that date.
6. Add cache invalidation in `useNutritionDashboard` after any retroactive mutation.

**Tests required**:
- Unit: `DatePickerModal` — future dates disabled; emits correct date string on select.
- Unit: `RetroactiveDiaryView` — renders meal sections; passes `targetDate` to add-item call.
- Integration: POST `/api/nutrition/diary-items` with past date → item appears in history.
- Integration: PATCH `/api/nutrition/diaries/[pastDate]` with water → history card updates.
